# 数据库设计：对话埋点与成本聚合

> 默认数据源：MySQL 8，库 `maibao_technology_application`（utf8mb4）。
> 连接串与账号在 `application.yml`（`DB_USERNAME` / `DB_PASSWORD` 走环境变量，密码放 `application-local.yml`，已 gitignore）。
> 建表由 Hibernate（`ddl-auto: update`）完成 —— 下面的 DDL 是**用 MySQL 数据源启动应用后**从库里导出的实际结构
> （导出方式：`SHOW CREATE TABLE user_query_log;`）。**注意**：用 H2 profile 跑是导不出这份 DDL 的。

---

## 1. 为什么拆两张表

| 表 | 角色 | 写入量 | 读法 |
|---|---|---|---|
| `user_query_log` | 明细流水，一次对话一行 | 随对话线性增长 | 按用户翻页（倒序） |
| `cost_accounting` | 按「用户 × 模型 × 天」聚合 | 每天每人每模型一行 | 直接查，不用扫明细 |

如果只有明细表，报表每次都要 `SUM()` 扫一大片；如果只有聚合表，出问题时没法定位到具体哪一次调用。两张表分工：明细负责可追溯，聚合负责可查询。

**权威与派生的关系**：明细是权威（先写、必成功），聚合是派生（可重算）。所以聚合写失败只记 `warn`，不影响对话，也不影响明细。

## 2. user_query_log

```sql
CREATE TABLE `user_query_log` (
  `id` bigint NOT NULL AUTO_INCREMENT,
  `request_id` varchar(64) NOT NULL,
  `user_id` varchar(64) NOT NULL,
  `model` varchar(64) NOT NULL,
  `source` varchar(16) NOT NULL,          -- SYNC / STREAM
  `prompt` varchar(2000) DEFAULT NULL,
  `reply` varchar(4000) DEFAULT NULL,
  `prompt_tokens` int NOT NULL,
  `completion_tokens` int NOT NULL,
  `total_tokens` int NOT NULL,
  `cost_amount` decimal(12,6) NOT NULL,
  `latency_ms` int NOT NULL,
  `status` varchar(16) NOT NULL,           -- SUCCESS / FAILED
  `error_msg` varchar(255) DEFAULT NULL,
  `created_at` datetime(6) NOT NULL,
  PRIMARY KEY (`id`),
  KEY `idx_query_user_created` (`user_id`,`created_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

设计要点：

- **`user_id + created_at` 联合索引**：为"按用户过滤 + 按时间排序"的列表查询而建，等值列在前、排序列在后。
- **prompt / reply 截断**（2000 / 4000）：明细表不适合存全文，完整内容应在对象存储或日志系统里。截断发生在应用层（`UsageService.truncate`），不是靠 DB 报错。
- **失败也落一行**：`status = FAILED`、`cost_amount = 0`，用于排查失败率；失败计入流水但**不计费、不进聚合**。
  - 注意：失败行的 `prompt_tokens / completion_tokens` **仍然按文本估算并写入**（reply 为空则 completion 为 0），所以「token 总量」和「计费 token」是两个口径。
- **`source` 区分 SYNC / STREAM**：两段代码路径，统计时要能分开看。
- **`request_id` 目前只做追踪号**：由服务端 `UUID.randomUUID()` 生成，**不是**上游传入的幂等键，不能用来去重。若要做幂等，需改成调用方生成并透传。

### ⚠️ 已知不一致 1：索引第二列用不上

| 项 | 内容 |
|---|---|
| 文档原说法 | "列表查询固定是某用户按时间倒序" → 索引 `(user_id, created_at)` 覆盖排序 |
| 实际实现 | `UserQueryLogRepository` 用的是 `findByUserIdOrderByIdDesc` / `findAllByOrderByIdDesc` → **`ORDER BY id DESC`** |
| 后果 | 索引第二列 `created_at` 用不上；过滤走 `user_id`，排序靠主键倒序扫描 |
| 建议 | 二选一：① 查询改成 `ORDER BY created_at DESC`（用上现有索引）；② 索引改成 `(user_id, id)`（更稳，因为 `id` 自增单调，`created_at` 由应用生成、可能因时钟/并发乱序） |

**推荐 ②**：`id` 与插入顺序严格一致，而 `created_at` 是应用侧 `Instant.now()`，理论上可能重复或回拨。

## 3. cost_accounting

```sql
CREATE TABLE `cost_accounting` (
  `id` bigint NOT NULL AUTO_INCREMENT,
  `user_id` varchar(64) NOT NULL,
  `model` varchar(64) NOT NULL,
  `stat_date` date NOT NULL,
  `request_count` bigint NOT NULL,
  `prompt_tokens` bigint NOT NULL,
  `completion_tokens` bigint NOT NULL,
  `total_tokens` bigint NOT NULL,
  `cost_amount` decimal(12,6) NOT NULL,
  `currency` varchar(8) NOT NULL,
  `updated_at` datetime(6) NOT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_cost_user_model_date` (`user_id`,`model`,`stat_date`),
  KEY `idx_cost_user_date` (`user_id`,`stat_date`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

设计要点：

- **唯一键 `(user_id, model, stat_date)`** 是幂等的锚点：一天一行，重复插入会被约束挡住，不会变成两行。
- **累加用 `UPDATE ... SET x = x + ?`**：并发下不会丢计数；返回 0 行说明当天还没有这行，再插入。
- **金额用 `decimal(12,6)` 而不是 double**：浮点累加会有精度漂移。
- **`stat_date` 用 DATE**：报表按天，不需要精确到毫秒。
- **`currency` 落在行上**：来自 `app.cost.currency`（默认 CNY），不是一个全局常量——换币种时历史行不受影响。

### 一个踩过的坑：间隙锁

最初把"先 UPDATE（没命中）再 INSERT"放在同一个事务里，结果 INSERT 被卡住 50 秒后报 `Lock wait timeout exceeded`。

原因：MySQL 默认 REPEATABLE READ 下，`UPDATE ... WHERE user_id=? AND model=? AND stat_date=?` 没命中行时，会在唯一索引上留下**间隙锁**；同一事务里的 INSERT 需要往这个间隙里插入，被自己的锁挡住。

改法（`usage/CostAccumulator.java`）：

1. `CostAccumulator.accumulate` **整个方法不加 `@Transactional`**；
2. UPDATE 走 `CostAccountingRepository.accumulate`（方法上有 `@Transactional`）→ **独立事务，执行完即提交、释放锁**；
3. 没命中 → 调 `CostRowCreator.create`，它是 `@Transactional(propagation = REQUIRES_NEW)` → **再开一个新事务插入**；
4. 撞唯一键抛 `DataIntegrityViolationException` → 说明别人先建行，**退回再累加一次**。

> 为什么用 `REQUIRES_NEW` 而不是普通 `@Transactional`：如果外层还包着事务，撞键会把**外层**标记成 `rollback-only`，后面的"退回累加"就白做了。

### ⚠️ 已知不一致 2：索引覆盖不了 `ORDER BY`

| 项 | 内容 |
|---|---|
| 文档原说法 | 索引 `(user_id, stat_date)`，按用户查当天/历史 |
| 实际实现 | `findByUserIdOrderByStatDateDescModelAsc` → **`ORDER BY stat_date DESC, model ASC`** |
| 后果 | `model` 不在索引里 → 排序仍需 filesort（数据量小时无感，量大时明显） |
| 建议 | 索引扩成 `(user_id, stat_date, model)`，让两个排序键都在索引里 |

### ⚠️ 已知不一致 3：日期取的是 JVM 时区

`CostAccumulator` 用 `LocalDate.now()` 取"今天"，用的是 **JVM 默认时区**；而连接串写了 `serverTimezone=Asia/Shanghai`。
如果服务器 JVM 时区不是 `Asia/Shanghai`，跨天那几个小时的数据会落到错误的 `stat_date`。

**建议**：统一用 `LocalDate.now(ZoneId.of("Asia/Shanghai"))`，或在启动时固定 `-Duser.timezone=Asia/Shanghai`。

## 4. 记账是同步的（这一点必须写清楚）

`UsageService.record()` 的顺序是：

```
① 写明细（user_query_log.save）     ← 同步，主路径
② 成功才累加（accumulator.accumulate）← 同步，异常被 catch 只打 warn
③ 失败调用直接 return（不累加）
```

**为什么同步**：本项目是"埋点旁路"的简化版 —— 一次对话结束就记账，不引 MQ，牺牲一点点延迟换取链路简单、可调试。

### 与真实平台实现的差异（面试时不要讲串）

| | 本项目（maibao） | 奇智真实平台（ibrain） |
|---|---|---|
| 记账触发 | 对话结束后**同步**调用 | 推理完成后发 **RocketMQ**，消费端异步记账 |
| 计数载体 | MySQL 聚合表 `UPDATE ... + ?` | **Redis `INCR`**（当日）+ DB 静态表（月） |
| 失败处理 | catch 后 `warn`，明细已在 | 监听器无脑 ack，有**丢账风险** |
| 幂等 | 唯一键 `uk_cost_user_model_date` | **缺失**（重复投递会多算） |

> 一句话：**本项目把"聚合表唯一键"当幂等锚点，真实平台是靠 Redis 累加、反而没有幂等**。讲的时候要说清是哪个系统。

## 5. 其余四张表

### publish_record（发布状态机）

| 字段 | 说明 |
|---|---|
| `status` | `SCHEDULED / PUBLISHING / SUCCESS / FAILED / CANCELLED` |
| `is_scheduled` | 0 = 立即，1 = 定时（来源标记） |
| `scheduled_at` | 到期时间 |
| **`claimed_at`** | **被抢占的时刻** —— 回收任务靠它判断"卡死"（`PUBLISHING` 且 `claimed_at` 超时）。**文档早期版本漏了这个字段** |
| `gray_percent` | 灰度进度 |
| `fail_reason` | 失败原因（截断 255） |

索引：`idx_status_scheduled_at (status, scheduled_at)` —— 对应"扫到期任务"的等值 + 范围查询。

### processed_task（MQ 消费去重）

| 字段 | 说明 |
|---|---|
| `task_id` | 唯一（`@Column(unique = true)`，**约束名由 Hibernate 自动生成**，不是手写命名） |
| `created_at` | 记录时间 |

去重靠**唯一约束 + 捕获 `DataIntegrityViolationException`**，不是"先查后插"。

### failed_task（重试耗尽落表）

| 字段 | 说明 |
|---|---|
| `task_id` | 索引 `idx_failed_task_id` |
| `payload` / `reason` | 各截断 512 |
| `attempts` | 重试次数 |
| `created_at` | 落表时间 |

### api_key（密钥）

| 字段 | 说明 |
|---|---|
| `owner_id` / `project_id` | 归属，用于越权校验 |
| `provider` | 厂商 |
| `cipher_text` | AES-GCM 密文（512） |
| `masked` | 脱敏串（64） |

### ⚠️ 已知不一致 4：api_key 缺索引

- **实际实现**：`KeyVaultService.list()` 走 `findByOwnerIdOrderByIdDesc`，按 `owner_id` 过滤；
- **现状**：实体上**没有任何索引**，列表查询会全表扫；
- **建议**：加 `@Index(name = "idx_apikey_owner", columnList = "owner_id")`。

## 6. 计费口径（模拟）

| 项 | 规则 |
|---|---|
| token 估算 | 中文（CJK）1 字 ≈ 1 token，其余 4 字符 ≈ 1 token（`TokenEstimator`，向上取整，非空文本最少 1） |
| 单价 | `app.cost.pricing`，按 model 的**冒号前缀**取价（`mock` / `openai`），取不到用 `default` |
| 金额 | `prompt_tokens × 输入单价/1000 + completion_tokens × 输出单价/1000`，`HALF_UP` 保留 6 位 |
| 失败调用 | 不计费（`cost_amount = 0`），也**不进聚合表**；但 token 仍按文本估算写入明细 |

这套口径只保证"可解释、可复现"，和厂商真实账单无关。

### ⚠️ 已知不一致 5：单价是 `double`

`CostProperties.Price` 的 `inputPer1k / outputPer1k` 是 `double`，而金额算出来是 `BigDecimal`。
`BigDecimal.valueOf(double)` 走 `Double.toString`，不会产生二进制噪音，但**单价本身仍是浮点**。

**建议**：单价也改 `BigDecimal`，让"单价 × 数量 / 1000"整条链路都是十进制。
