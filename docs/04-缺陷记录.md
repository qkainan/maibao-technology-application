## BUG-001 消费终态失败没有回写 outbox

**位置**：`mq/TaskConsumer.handleFailure` 的终态分支

**现象**

消费失败走到终态（不可重试，或重试耗尽）时，代码只写了 `failed_task` 并把消息 nack 进 DLQ，没有通知 outbox。outbox 仍停在 `SENT`，5 分钟后对账任务把它打回 `PENDING` 重投：

```
消费失败 → failed_task + nack 进 DLQ
outbox 仍是 SENT（没人 markConsumed）
  ↓ 300s 后 reconcile
打回 PENDING → 重投 → 再失败 → 又一条 failed_task + 又一条 DLQ
  ↓ 重复
直到 outbox.attempts 用到上限
```

**影响**

默认参数（`max-retries=3`、`consume-timeout=300s`、`outbox-max-attempts=5`）下：

| 错误类型 | 每轮投递次数 | 轮数 | 业务调用 | failed_task | DLQ |
|---|---|---|---|---|---|
| 可重试 | 4（attempt 0/1/2/3） | 5 | **20 次** | 5 条 | 5 条 |
| 不可重试 | 1 | 5 | **5 次** | 5 条 | 5 条 |

业务调用就是一次模型请求，20 次是真实成本。另外，修复前遗留的 `SENT` 行也会在下一次对账时被"复活"——实测中一条更早的 `nokey-1` 就被重新投递并再次失败。

**复现**（把时间压到秒级）

```bash
java -jar app.jar \
  --app.mq.max-retries=0 \
  --app.mq.consume-timeout-seconds=8 \
  --app.mq.outbox-reconcile-ms=3000 \
  --app.mq.outbox-reconcile-initial-delay-ms=2000 \
  --app.mq.outbox-max-attempts=2

# 提交一条必然失败的任务（没有配置 key）
curl -X POST 'http://127.0.0.1:8080/api/task/submit?payload=x&taskId=loop-1&model=openai:gpt-4o'
# 注：复现时任务链路仍启用。现在该接口已删除（见 docs/01 §4），
# 成本链路也已改走 Redis（见 BUG-004），当前没有消费者在用这套终态写回逻辑；
# 代码保留在 mq/outbox 与 TaskConsumer，等长任务接入再启用。
```

实测结果：`failed_task=2`、业务调用 `2` 次、DLQ `+3`（含被复活的旧消息）、outbox 最终 `FAILED attempts=2`，日志出现两次 `outbox reconcile: requeued=...`。

**根因**

`markConsumed` 只在成功与重复投递两个分支调用；终态分支只写 `failed_task` + `basicNack`。

**修复**

1. 新增 `OutboxRepository.markFailedByMessageId(...)`，带状态护栏 `status in ('PENDING','SENT')`；
2. 终态分支在 **nack 之前** 调用它，把 outbox 直接标 `FAILED` 并记录原因；
3. 重投分支不碰 outbox（否则正常重试会被提前判死）。

顺序很重要：先 nack 再写 outbox 的话，中间崩溃会留下 `SENT`，对账又会把它放出来。

**回归**

- `TaskConsumerTest`：终态分支断言 `markFailedByMessageId` 被调用；重投分支断言从未调用。
- 端到端：同样参数下只产生 `failed_task=1`、业务调用 `1` 次、DLQ `+1`，outbox `FAILED attempts=0`，对账日志不再出现该消息。

## BUG-002 `markRetry` / `markFailed` 缺少状态条件

**位置**：`mq/repository/OutboxRepository`

**现象**

```java
// 修复前
update OutboxMessage o set o.status = :pending, o.attempts = o.attempts + 1 ...
where o.id = :id
```

只有 `id`，没有前置状态。一条迟到的 nack 打在已经 `CONSUMED` 的行上，会把它打回 `PENDING`，于是又投一次；打在 `FAILED` 上则会把失败记录复活。`markFailed`（returns 回调）同样如此。

**触发条件**

同一个 outbox 行因租约到期被 publish 两次时，两次 publish 共用同一个 `CorrelationData` id。如果第二次的 nack 落在第一次已经消费完成的行上，就会命中。

概率低，但代价是把已经完成的消息重新投递；而状态护栏是零成本的。

**修复**

```java
where o.id = :id and o.status in ('PENDING', 'SENT')
```

`markFailedByMessageId`（BUG-001 新增）同样带这个护栏。`markSent`、`markConsumed` 原本就有状态条件，不受影响。

**回归**

JPQL 层面没有单测，靠代码评审与端到端验证；后续若引入 `@DataJpaTest`，应补一条"CONSUMED 行收到 nack 不变"的用例。

## BUG-003 对账任务的首次延迟硬编码

**位置**：`mq/OutboxPublisher.reconcile`

**现象**

```java
@Scheduled(fixedDelayString = "${app.mq.outbox-reconcile-ms:60000}", initialDelay = 60000)
```

周期可配，首次延迟不可配。压测时想缩短只能改代码；运维也不能按环境调整。

**修复**

改为 `${app.mq.outbox-reconcile-initial-delay-ms:60000}`，默认值不变。

## BUG-004 成本链路用 outbox 逐条投递，吞吐上限只有 10 条/秒

**位置**：`usage/CostConsumer`（已删除）、`mq/OutboxPublisher`

**现象**

这个项目的目标场景是 Agent：**一次用户操作会打出上百次模型调用**，对话 QPS 约 1000。原链路是"一次对话一条成本消息"，于是：

- `OutboxPublisher` 是 `findTop20 / 2000ms` → **投递上限 10 条/秒**；
- 每条消息要走 6 次 DB 写（claim / confirm 回写 `SENT` / 去重插入 / 累加 UPDATE / 消费回执 / 失败时 `markRetry`）；
- `cost_accounting` 同一 `(user, model, date)` 是单行热点，4 并发只拿到约 3 倍提升。

结果：QPS 一超过 10，`mq_outbox` 的 `PENDING` 就永久积压，成本聚合永远追不上对话量。**这不是参数没调好，是形态不对。**

**根因**

粒度选错。成本累加是可合并的聚合（`+= sum`），却按"一条消息 = 一次累加"实现：

- 消息量 = 请求量；
- 每条消息一次状态机往返；
- 投递速率还被 `findTop20` + `2s` 写死，且**没有任何地方会报错**——它只是慢。

**修复**

1. 成本累加改 Redis：`HINCRBY`（`long × 1e8`），一次 pipeline 代替 6 次 DB 写；
2. 明细改本地队列 + `JdbcTemplate.batchUpdate`，200ms 一批；
3. `CostFlushJob` 每分钟 `HGETALL` → **覆盖写** `cost_accounting`（`ON DUPLICATE KEY UPDATE`），幂等不再需要去重表；
4. 删除 `CostConsumer` / `CostProcessor` / `CostDedupeService` / `CostRowCreator` / `cost_message_log`；
5. outbox 收进 `mq/outbox/`，默认关闭（`app.mq.outbox-enabled=false`）。

**回归**

| 项 | 修复前 | 修复后 |
|---|---|---|
| 每次对话的 DB 写 | 6 次 | **0 次**（明细入队 + Redis pipeline） |
| 投递吞吐上限 | 10 条/秒 | 无投递环节 |
| 聚合写入 | 逐条 `UPDATE ... += ?`（单行热点） | 每分钟一次覆盖写 |
| 幂等手段 | `cost_message_log` 唯一键 | 覆盖写天然幂等 |

幂等验证：同一分钟重复跑 `CostFlushJob` 多次，`cost_accounting.cost_amount` 不变。

**复盘**

1. **选 MQ 之前先问两句**：这条消息能不能合并？丢了能不能重算？两个都为"是"的，不需要强投递。
2. **容量要按"每条消息的 DB 写次数 × QPS"算**，不能只看 QPS 本身。这里 1000 QPS × 6 = 6000 写/秒，一眼就知道撑不住。
3. **参数写死的扫描器是隐性天花板**：`findTop20` + `2000ms` 把系统上限定在 10 条/秒，而它不会报错、不会告警，只会越积越多。
4. **反过来也要记住**：outbox 仍然有价值——它解决的是"不能丢"，不是"撑不住"。可合并的计数走 Redis，必须逐条持久化、要跨系统的才走 MQ。

## BUG-005 价表配置被误删，成本恒为 0（静默丢账）

**位置**：`application.yml` 的 `app.cost.pricing`、`usage/CostCalculator`

**现象**

改造成本链路时，我用正则整块替换 `app.cost.*`，匹配范围是 `app.cost:` 到下一个顶层键
（当时是 `logging:`）。而 `pricing` 恰好排在 `cost` 块的最后 —— **被一起替换掉了**。

后果非常隐蔽：

- 应用正常启动，日志没有 ERROR；
- 对话正常返回，明细正常落库；
- Redis 里 `pt / ct / cnt` 都有值，**只有 `cost` 是 0**；
- 配额接口 `used` 永远是 0，**永远拦不住超限**；
- 对账也发现不了：Redis 和 DB 都是 0，两边一致。

**根因**

`CostCalculator.priceFor()` 取不到配置时返回 `new CostProperties.Price()`（全 0），
所以"配置缺失"被降级成了"单价为 0"，而不是报错。

**修复**

1. 把 `pricing` 段补回 `application.yml`；
2. **加启动自检**：`CostCalculator` 上 `@PostConstruct`，价表为空直接 `log.error`，
   让这类配置错误在启动时暴露，而不是等对账。

**回归**

```
# 修复前
redis: u_fix|mock:echo|cost = 0        pt=8 ct=16 cnt=2
/api/quota: used = 0

# 修复后
redis: u_fix|mock:echo|cost = 4000     pt=8 ct=16 cnt=2   （4000 / 1e8 = 0.00004 元）
/api/quota: used = 0.00004000
```

**复盘**

1. **"配置缺失"不要降级成"默认值 0"** —— 金额这类字段，默认值应该让程序叫出来。
2. **正则替换整块配置时必须校验结果**：替换后再读一遍，确认关键键还在。
3. **静态检查查不出这类问题**：括号平衡、import 都对，只有真的跑起来打一次请求才看得见。
4. 这次是"端到端验证"抓到的 —— 编译通过、单测全绿、日志无异常，**但业务数字是错的**。

## 复盘：这类问题的共同点

1. **状态机有两端，只写一端就会自愈成"重试风暴"**。消费端判定"终态失败"后，生产端的 outbox 也必须进入终态；否则对账这个"补偿机制"会变成"放大器"。
2. **所有状态迁移的 UPDATE 都要带前置状态**。没有前置状态的 UPDATE 在迟到消息、重复投递、租约重发下都会出错，而且很难在正常路径上发现。
3. **补偿任务要能区分"没做完"和"做失败了"**。`SENT` 既可能是"在途"也可能是"已经失败但没人回写"，所以终态必须显式落库，不能靠超时推断。
