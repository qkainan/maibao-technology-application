## 1. 适配器模式：统一多厂商出入参

**代码位置**
- `adapter/AiProviderAdapter.java` — 适配器接口（含 `capabilities()`）
- `adapter/OpenAiCompatibleAdapter.java` — OpenAI 兼容协议实现（HTTP + 真流式）
- `adapter/MockAdapter.java` — 无 key 兜底
- `adapter/AdapterRegistry.java` — 按 model 前缀查表
- `adapter/domain/Capabilities.java`、`ProviderError.java` — 能力声明与归一错误码

**设计要点**

上层只依赖 `ChatRequest` / `ChatChunk` 这一套统一结构。每个厂商自己负责把自家协议翻译成这套结构：OpenAI 是 `choices[0].delta.content`，思维链是 `reasoning_content`，有些厂商是 `result`。新增一个厂商 = 新增一个实现类，注册表不用改，上层也不用改。

两条容易被忽略的约束：

- **能力要显式声明**。`capabilities()` 返回是否支持流式、视觉、工具调用和最大 token 数；上层据此校验和降级，而不是写 `if (model.startsWith("gpt-4o"))`。
- **错误码必须归一**。厂商的 401 / 429 / timeout / content filter 统一成 `AUTH` / `RATE_LIMIT` / `TIMEOUT` / `FILTERED` / `SERVER`，上层才能写统一的重试策略（`AUTH` 不重试、`RATE_LIMIT` 退避、`TIMEOUT` 有限重试）。

**常见疑问**

- 和策略模式的区别？→ 适配器解决"接口不兼容"，策略解决"算法可替换"；这里两者都用到了（适配 + 按 model 选实现）。
- 为什么用注册表而不是 if-else？→ 开放封闭：加厂商不改已有代码，也方便按配置灰度。

## 2. 循环节点

**代码位置**
- `workflow/LoopNode.java`
- `workflow/LoopNodeTest.java`

**设计要点**

循环变量每轮结束写回，下一轮通过它读上一轮的结果；终止条件在**轮末**求值，所以能引用本轮产出；外面还有 `maxCount` 兜底 —— 条件是用户配的，可能永远不成立，没有上限就是死循环。

**常见疑问**

- 为什么上限要有范围校验？→ `(0, 100]`，配置错误在构造节点时直接拒绝，而不是运行时才炸。
- 和迭代（Iteration）的区别？→ 迭代是遍历数组、子图嵌套；循环是控制流重复，结构扁平，靠起止标记界定循环体。
- 中途取消怎么停？→ 状态位 + 每轮开始前检查。本项目尚未实现，属于后续计划。

## 3. SSE 流式链路

**代码位置**
- `chat/stream/SseFrameParser.java` — 帧切分
- `chat/stream/ChunkNormalizer.java` — 多厂商归一
- `chat/stream/OpenAiSseDecoder.java` — 按行喂入，切帧 + 归一 + `[DONE]`
- `chat/stream/SseStreamSession.java` — 事件序号、心跳、取消、线程安全发送
- `controller/ChatController.java` — 建连接后把读取交给流式线程池
- `static/index.html` — 浏览器端测试台（`EventSource`）

**设计要点**

一次流要同时做对六件事：

| # | 点 | 这里的做法 |
|---|---|---|
| 1 | 不占容器线程 | `SseEmitter` + 独立线程池，Controller 立即返回 |
| 2 | 帧解析 | 自攒 buffer 按空行切帧，多行 `data:` 拼接（`SseFrameParser`） |
| 3 | 增量归一 | `delta` / `result` / `reasoning_content` → `ChatChunk`（`ChunkNormalizer`） |
| 4 | 心跳 | 每 15s 发 `: keep-alive` 注释帧，避免网关 60s 空闲断连 |
| 5 | 取消传播 | 写失败 → `cancelled=true` → 适配器停止读上游并关闭连接 |
| 6 | 事件序号 | 每个事件带自增 `id`，便于去重与排查 |

超时分层：连接 5s（HttpClient 建连）、首字节 30s（请求级 timeout）、整体 300s（读循环里的 deadline）。

**常见疑问**

- 为什么不用 WebSocket？→ 单向推送够用、复用 HTTP 鉴权与网关，还能直接用浏览器 `EventSource`。
- 为什么服务端要转发，不让前端直连厂商？→ `EventSource` 只支持 GET、不能带自定义 Header；真实场景需要 POST + `Authorization`。
- 断线能续传吗？→ 不能。模型输出不可续，重连等于重新生成；前端保留已显示内容并用事件 id 去重，不做"从断点续传"。
- 取消后上游真的停了吗？→ 适配器每读一行检查一次 `cancelled`，断开后下一次检查就会抛出并关闭流；慢速流实测只产生 7 个 token 的流水。

## 4. 成本记账：Redis 累加 + 明细批量落库（MQ 退居备用）

**代码位置**
- `usage/UsageService.java` — 埋点入口：明细入队 + Redis 累加，两件都不碰 DB 热路径
- `usage/CostRedisStore.java` — Redis 封装（pipeline 累加、按天 Hash、配额读）
- `usage/DetailBuffer.java` — 明细批量缓冲（200ms 一批，`JdbcTemplate.batchUpdate`）
- `usage/CostFlushJob.java` — 每分钟覆盖写 `cost_accounting` + 每日日结
- `usage/CostQuotaService.java`、`QuotaExceededException.java` — 配额校验（业务码 4029）
- `usage/CostAccumulator.java` — 只剩一层 Redis 封装，不再碰数据库
- `mq/outbox/` — outbox 独立成包，默认关闭，作为"必须强投递"时的备用组件

**为什么把 MQ 从成本链路里摘出去**

按容量算一遍就清楚了：Agent 场景 QPS≈1000，一次对话一条成本消息，而每条消息要 **6 次 DB 写**（claim / confirm 回写 `SENT` / 去重插入 / 累加 UPDATE / 消费回执 / 失败时 `markRetry`），也就是**约 6000 次写/秒**；`cost_accounting` 同一 `(user, model, date)` 又是单行热点。这不是参数没调好，是**粒度选错**——成本累加是可合并的聚合（`+= sum`），却按"一条消息一次累加"实现。可合并的东西不需要排队。

**设计要点**

三段各解决不同问题：

| 段 | 手段 | 解决什么 |
|---|---|---|
| 明细（必须逐条持久化） | 本地队列 + 200ms 批量 INSERT | 1000 QPS 下逐条 INSERT 会把连接池与 redo log 打满 |
| 成本累加（可合并） | Redis pipeline，`long × 1e8` | 一次 O(1) 内存操作代替 6 次 DB 写 |
| 成本落盘（可重算） | 每分钟 `HGETALL` + **覆盖写** | 幂等靠"覆盖状态"，不靠"去重事件" |

**覆盖写是整个方案的关键**：

```sql
ON DUPLICATE KEY UPDATE cost_amount = VALUES(cost_amount)
```

Redis 里存的就是"当日截至目前的累计值"，落盘只是把它同步到 DB。重跑任意多次结果一致，所以**不需要去重表、不需要水位线、不需要 outbox**。原来的 `cost_message_log` 表随之删除。

**明细为什么用 `JdbcTemplate` 而不是 JPA**：`user_query_log` 主键是 `IDENTITY`，Hibernate 遇到 IDENTITY 会**关掉 JDBC 批量**，`saveAll` 实际退化成逐条 INSERT。要真批量只能自己写多值 INSERT。

**配额放在调用之前**：`ChatService` 入口先 `quotaService.check(userId)`，超限直接抛 4029，**不调模型、不产生费用**。读的是 Redis 的当日累计（O(1)），不查 DB。Redis 不可用时**放行**——配额是成本控制不是安全边界，不能因为缓存故障把业务全阻断。

**常见疑问**

- 为什么不用 MQ 投成本？→ 累加可合并，"一条消息一次累加"是把可合并的操作排队；1000 QPS 下要 6000 次 DB 写/秒。**可合并的走 Redis，必须逐条持久化、要跨系统的才走 MQ。**
- 落盘为什么是覆盖写？→ Redis 存的就是当日累计，覆盖天然幂等；累加写要额外去重表，还要处理重复消息。
- 明细丢了怎么办？→ 队列满时丢弃并计数，丢的只是"可追溯性"，成本已经在 Redis 里累加；反过来 Redis 挂了，未落盘的部分可以从未清理的明细重算。
- Redis 挂了对话能用吗？→ 能。配额校验放行、累加失败只 warn，对话不受影响；恢复后继续累加。
- 明细为什么只留 7 天？→ 1000 QPS 一天 8640 万行，按 1–2 KB/行就是 86–170 GB/天，必须瘦身 + 分区 + 归档；生产应换成按天分区 + `DROP PARTITION`。
- outbox 还留着干嘛？→ 它不是为成本设计的，是为"必须强投递"的消息（通知、扣费、跨系统事件）准备的。现在默认关闭（`app.mq.outbox-enabled=false`），需要时打开。
- 为什么金额存 `long × 1e8`？→ 浮点累加会漂移；定点整数在 Redis 里 `HINCRBY` 也是整数自增，落盘时再折算 `BigDecimal(值, 8)`。

## 5. 多线程与锁：发布状态机的乐观锁

**代码位置**
- `publish/repository/PublishRepository.java` — 条件更新（改状态 + 记录抢占时刻）
- `publish/PublishService.java#scanAndClaimDue` / `execute` / `recoverStuck` — 抢占、执行、卡死回收
- `publish/PublishExecutor.java` — 执行线程池（与 Web 线程隔离）
- `publish/PublishHandler.java` / `SimulatedPublishHandler.java` — 真正的发布动作
- `publish/PublishScheduler.java` — 扫描与回收的触发器
- `publish/domain/PublishRecord.java` — 表上声明了 `idx_status_scheduled_at (status, scheduled_at)`

**设计要点**

状态迁移不是先查再改，而是 `UPDATE ... SET status=新值 WHERE id=? AND status=旧值`。返回 0 就说明别人已经推进了，直接返回。`/race` 接口用 20 个线程抢同一条记录，正确结果是只成功 1 个 —— 这是验证乐观锁的方式。

抢占成功不等于结束：执行交给独立线程池，跑完按结果推进 `SUCCESS` / `FAILED`。执行线程和回收线程可能同时动作，但两边都是条件更新，只有一个能改成功 —— 失败的一方拿到 0 行，日志里记 `state advanced: false`。

**常见疑问**

- 执行线程挂了怎么办？→ `recoverStuck` 扫描停留在 `PUBLISHING` 超过阈值的记录，标记为 `FAILED` 并写明原因；否则它会永久卡住。
- 乐观锁 vs 悲观锁？→ 冲突少用乐观锁（无阻塞），冲突多用悲观锁/分布式锁。
- ABA？→ 状态单向推进不回退，不存在 ABA；若状态可回退则要版本号。
- 冲突率高会不会打爆 DB？→ 会。要配合前端防抖 + 冲突直接返回而不是无脑重试。
- 执行池为什么 `CallerRunsPolicy`？→ 队列满时回退到调度线程执行，形成背压；丢任务会让记录停在 `PUBLISHING`。

## 6. 密钥加密：密文入库与归属校验

**代码位置**
- `security/AesGcmCipher.java` — AES-GCM 加解密 + 脱敏
- `security/KeyVaultService.java` — 写入加密 / 列表脱敏 / **归属校验**
- `controller/ApiKeyController.java` — 越权校验接口

**设计要点**

明文不落库，只在用的时候解密；列表返回脱敏串；读取时强制带 ownerId，别人的 key 直接 403。**前端过滤不算权限控制** —— 那只是"不显示"，改个参数就拿到了。

**常见疑问**

- 为什么 GCM 不是 CBC？→ GCM 自带完整性校验（tag），能发现密文被篡改。
- 密钥本身怎么管？→ 本项目放在配置里；部署时应放 KMS / 环境变量，不能进代码库。
- 为什么用唯一约束去重而不是先查后插？→ 并发下"先查后插"有竞态。

## 7. 构建与发布：分层缓存与反向代理

**代码位置**
- `Dockerfile` — 分层顺序 + 多阶段
- `deploy/nginx.conf` — `try_files` 回退 + SSE 关缓冲
- `.github/workflows/ci.yml` — CI 构建与测试

**设计要点**

如果按 `COPY . .` 再 `mvn dependency` 的顺序，改一行代码就会让依赖层全部失效，每次重新拉依赖。改成先 `COPY pom.xml` 再 `COPY src`，依赖层就稳定命中缓存。再叠加多阶段构建，最终镜像里只有 jar 和 JRE。

**常见疑问**

- 前端刷新 404 的根因？→ history 路由请求真实路径，Nginx 找不到文件；`try_files $uri $uri/ /index.html` 回落。
- SSE 反代要注意什么？→ `proxy_buffering off`，否则增量被 Nginx 攒着一起发，前端看起来"卡住然后一次性出来"。

## 8. 范围边界

| 外部系统承担的部分 | 本项目的处理 |
|---|---|
| XXL-Job 定时调度 | `@Scheduled`，只实现"扫描 + 抢占"这一层 |
| 灰度切流由调度服务执行 | 只记录 `grayPercent`，不做切流 |
| 工作流执行引擎（DAG 调度、并行分支） | 只做线性节点 + 循环节点 |
| 多租户、审计、权限体系 | 只做密钥归属校验 |
| 生产级 RabbitMQ 集群 + 死信 | 单机；手动 ack + confirm/returns + 有限重试 + 失败表，不配 DLX |

这些边界是有意保留的：把一个机制讲透，比假装覆盖一张能力清单更可信。维护时以这张表为准，不要顺手把没实现的能力写进文档。
