## 0. 一句话定位

## 1. 当前跑的链路

```
POST /api/chat  (同步)           GET /api/chat/stream  (SSE)
        │                                  │
        └──────────────┬───────────────────┘
                       ▼
                  ChatService
                   ├─ ① CostQuotaService.check(userId)   → Redis HGET（超限抛 4029）
                   ├─ ② adapter.chat() / stream()        → 唯一的慢动作
                   └─ ③ UsageService.record(...)
                            ├─ DetailBuffer.offer(record)      → 内存队列，零 IO
                            └─ CostRedisRepository.increase()  → Redis pipeline（7 条命令）
                       ▼
                  返回 reply（不等落库）

【后台】DetailBuffer  每 200ms 攒批
          ├─ mode=mq  → maibao.detail.exchange → queue
          │                └─ DetailConsumer（手动 ack + x-retry-count ×3 + DLQ）→ 批量 INSERT IGNORE
          └─ mode=local / MQ 发送失败 → DetailWriter 直写

【后台】CostFlushJob   每 60s  HGETALL → 覆盖写 cost_accounting
                      每天 00:05 最后一次落盘 → DEL 当日 key → 清理 7 天前明细
【后台】CostReconcileJob 每 300s Redis 累计 vs DB 聚合，差异超阈值告警
```

其他链路（互不依赖）：
- **发布**：`publish_record` 状态机 + 条件更新抢占 + 执行线程池 + 卡死回收（`@Scheduled` 扫表，不走 MQ）
- **SSE**：控制器建连即释放容器线程，读上游在独立线程池，15s 心跳，断连取消
- **密钥**：AES-GCM 密文入库 + 归属校验（越权 4030）

## 2. MQ 现在在做什么

**只有一件事：明细落库。**

| 链路 | 状态 | 入口 |
|---|---|---|
| **明细落库**（`maibao.detail.*`） | ✅ 活跃，默认 `mode=mq` | `DetailBuffer.flush()` |
| 异步任务（`maibao.task.*`） | ⛔ 停用 | `/api/task/submit` 已删除；`app.task.enabled=false` |
| outbox 组件（`mq/outbox/`） | ⛔ 默认关闭 | 无人调用 `enqueue`；`app.mq.outbox-enabled=false` |

`RabbitConfig` 仍声明 task + detail 两套拓扑（task 那套是给未来长任务预留的）。

**定位说明（面试要主动讲）**：
- 本项目是**单应用**，明细走 MQ 的目的是让可靠性机制（confirm/returns/DLX/重试/幂等/死信）有真实负载；
- 真实平台（ibrain）用 RocketMQ 的理由不同：**成本消息来自多个上游通道（通用/百度/百川），是跨系统汇聚**，本地队列做不到；
- 单应用下"本地队列 + 失败重入队"其实够用，差别只在**重试的账本在内存还是持久化**。

## 3. 成本记账的三段（核心设计）

| 段 | 手段 | 解决什么 |
|---|---|---|
| 明细（必须逐条持久化） | 本地队列 200ms 攒批 → MQ → 批量 `INSERT IGNORE` | 1000 QPS 下逐条 INSERT 打满连接池；进程被杀不丢 |
| 成本累加（**可合并**） | Redis pipeline，`HINCRBY` ×5，金额 `long×1e8` | 6 次 DB 写/条 → 1 次内存操作 |
| 成本落盘（**可重算**） | 每分钟 `HGETALL` + **覆盖写** `cost_amount = VALUES(...)` | 幂等靠"覆盖状态"，不需要去重表 |

Redis 键（按天分桶，TTL 3 天）：
```
maibao:cost:acc:{yyyyMMdd}   Hash  field = userId|model|{cost|pt|ct|cnt}  → 落盘
maibao:cost:user:{yyyyMMdd}  Hash  field = userId                        → 配额 O(1) 读
```

配额：`ChatService` 入口先校验，超限抛 `QuotaExceededException`（业务码 **4029**），不调模型、不产生费用。Redis 不可用时**放行**（配额是成本控制，不是安全边界）。

```
maibao.tech
├── adapter/   多厂商适配（Mock / OpenAI 兼容）+ SSE 解码 + 错误归一
├── chat/      ChatService（配额 → 调模型 → 埋点）
├── workflow/  节点模型、循环节点、图校验
├── publish/   发布状态机、乐观锁抢占、执行线程池、卡死回收
├── security/  AES-GCM、密钥归属校验
├── mq/
│   ├── RabbitConfig        两套拓扑（task / detail）+ confirm/returns 回调
│   ├── TaskConsumer/Processor/DedupeService   任务链路（停用，代码保留）
│   ├── domain/             TaskMessage / ProcessedTask / FailedTask
│   ├── repository/
│   └── outbox/             outbox 独立成包（默认关闭，备用）
└── usage/     11 个类在根目录 + 3 个子包
    ├── UsageService        入口：明细入队 + Redis 累加
    ├── CostQuotaService    配额拦截
    ├── CostCalculator      计价 / TokenEstimator
    ├── CostProperties      配置（只有数据）
    ├── CostKeys            Redis 键拼装
    ├── CostAggregate       落盘单位（record，带 costYuan()）
    ├── CostRedisRepository Redis 存取（pipeline / 聚合 / 日结）
    ├── CostFlushJob        覆盖写 + 日结
```

表：7 张（`user_query_log`、`cost_accounting`、`publish_record`、`processed_task`、`failed_task`、`mq_outbox`（备用）、`api_key`）。

## 6. 已有取舍（每条都能被追问）

| 取舍 | 选择 | 理由 |
|---|---|---|
| 成本累加放哪 | **Redis**，不是 MQ | 累加可合并；一条消息一次累加是 6 次 DB 写/条 |
| 成本如何落库 | **覆盖写**，不是 `+=` | Redis 存的是当日累计，覆盖天然幂等，不需要去重表 |
| 明细怎么落库 | **MQ 批量**，不是直接 `save` | 直接 save 时 DB 抖动会让"对话失败"（模型其实成功）；本地方案躲不开 `kill -9` |
| 幂等靠什么 | **唯一键 + `INSERT IGNORE`** | 不需要额外去重表 |
| 配额超限 | **拒绝**（4029） | 与 ibrain 的"默认放行"相反；本项目选可用性之外的严格 |
| 框架重试 | **不开**（生产 + 消费） | 与 outbox / 消息头重试重复；会把消费者线程钉住 |
| 死信 | **`failed_task` 表 + DLQ 双轨** | 表给人查，DLQ 给重放 |
| 单应用为何用 MQ | **让机制有负载 + 预留多生产方** | 不吹"必须" |

## 9. 三条可直接复用的口径

1. **可合并的计数走 Redis，必须逐条持久化、要跨系统的才走 MQ。**
2. **outbox 解决"不能丢"，Redis 解决"撑不住"。** 选哪个看瓶颈是哪一个。
3. **不是"能不能重试"的差别，是"重试的账本存在哪"的差别** —— 内存 vs 消息头 vs 数据库行。
