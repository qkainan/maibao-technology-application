# 数据库设计

> MySQL 8 · utf8mb4 · InnoDB · 库 `maibao_technology_application`
> **结构以 `docs/schema.sql` 为准**：库里已按该脚本重建过（2026-10-25 验证）。
> 应用侧配置为 `spring.jpa.hibernate.ddl-auto: validate`，启动时只校验、不改结构。

---

## 1. 全景

| 表 | 角色 | 写入频率 | 主要读法 |
|---|---|---|---|
| `user_query_log` | 对话明细流水（一次调用一行） | 每次对话 | 按用户翻页、按时间范围统计 |
| `cost_accounting` | 成本聚合（用户 × 模型 × 天） | 每次成功对话 | 直接查，不扫明细 |
| `publish_record` | 发布状态机 | 每次发布 / 每轮扫描 | 扫到期、扫卡死 |
| `processed_task` | MQ 消费去重 | 每条消息 | 唯一键判重 |
| `failed_task` | 重试耗尽的失败留痕 | 少量 | 按 task_id 查、人工补偿 |
| `mq_outbox` | 本地消息表（先落库再投递） | 每次对话（成本事件） | 扫 PENDING、对账 SENT |
| `cost_message_log` | 成本消息去重 | 每条成本消息 | 唯一键判重、7 天后清理 |
| `api_key` | 密钥密文与脱敏串 | 少量 | 按 owner 列表 |

**两条主线**：

- **明细 → 聚合**：`user_query_log` 是权威（先写、必成功），`cost_accounting` 是派生（可重算）。聚合写失败只告警，不影响对话。
- **状态机 + 去重表**：`publish_record` 靠条件更新推进状态，`processed_task` 靠唯一键挡重复消息。

## 2. 建表脚本

```sql
SET NAMES utf8mb4;

-- ========== 2.1 对话明细流水 ==========
CREATE TABLE IF NOT EXISTS `user_query_log` (
  `id`                bigint       NOT NULL AUTO_INCREMENT COMMENT '自增主键',
  `request_id`        varchar(64)  NOT NULL                COMMENT '请求追踪号（UUID），同时作为幂等锚点',
  `user_id`           varchar(64)  NOT NULL                COMMENT '用户标识，空值归入 anonymous',
  `model`             varchar(64)  NOT NULL                COMMENT '模型名，可带厂商前缀，如 mock:demo',
  `source`            varchar(16)  NOT NULL                COMMENT '调用入口：SYNC / STREAM',
  `prompt`            varchar(2000) DEFAULT NULL           COMMENT '问题原文，超长截断',
  `reply`             varchar(4000) DEFAULT NULL           COMMENT '回答原文，超长截断',
  `prompt_tokens`     int          NOT NULL                COMMENT '输入 token 估算值',
  `completion_tokens` int          NOT NULL                COMMENT '输出 token 估算值',
  `total_tokens`      int          NOT NULL                COMMENT '总 token 数',
  `cost_amount`       decimal(12,6) NOT NULL               COMMENT '本次费用（元），失败为 0',
  `latency_ms`        int          NOT NULL                COMMENT '耗时（毫秒）',
  `status`            varchar(16)  NOT NULL                COMMENT 'SUCCESS / FAILED',
  `error_msg`         varchar(255) DEFAULT NULL            COMMENT '失败原因',
  `created_at`        datetime(6)  NOT NULL                COMMENT '落库时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_query_request` (`request_id`),
  KEY `idx_query_user_id` (`user_id`, `id`),
  KEY `idx_query_created` (`created_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='对话明细流水';

-- ========== 2.2 成本聚合 ==========
CREATE TABLE IF NOT EXISTS `cost_accounting` (

  `updated_at`        datetime(6)   NOT NULL                COMMENT '最后更新时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_cost_user_model_date` (`user_id`, `model`, `stat_date`),
  KEY `idx_cost_user_date_model` (`user_id`, `stat_date`, `model`),

-- ========== 2.4 MQ 消费去重 ==========
```

## 3. 表设计与索引说明

### 3.1 user_query_log

| 索引 | 列 | 服务哪个查询 |
|---|---|---|
| `PRIMARY` | `id` | 主键 |
| `uk_query_request` | `request_id` | 幂等锚点；按追踪号反查 |
| `idx_query_user_id` | `user_id, id` | 列表：`WHERE user_id = ? ORDER BY id DESC` |
| `idx_query_created` | `created_at` | 全局时间范围统计（按天出报表） |

要点：

- **排序键用 `id` 而不是 `created_at`**：`id` 自增单调，天然等于插入顺序；`created_at` 由应用生成，可能重复或回拨。索引第二列放 `id` 才能真正消除 filesort。
- **`prompt` / `reply` 在应用层截断**（2000 / 4000 字符），DB 只做兜底长度限制；全文应放对象存储或日志系统。
- **失败也落一行**：`status = FAILED`、`cost_amount = 0`，用于算失败率；**token 仍按文本估算写入**，所以「token 总量」与「计费 token」是两个口径。
- **`request_id` 是幂等锚点**：由调用方传入（当前实现是服务端 UUID），有了唯一键之后，"同一请求重复写"会被 DB 挡住，可以直接用来做重试幂等。

### 3.2 cost_accounting

| 索引 | 列 | 服务哪个查询 |
|---|---|---|
| `uk_cost_user_model_date` | `user_id, model, stat_date` | 累加定位 + 幂等（一天一行） |
| `idx_cost_user_date_model` | `user_id, stat_date, model` | `WHERE user_id=? ORDER BY stat_date DESC, model ASC` |
| `idx_cost_date` | `stat_date` | 跨用户按天出报表 |

要点：

- **唯一键是幂等锚点**：`(user_id, model, stat_date)` 保证一天一行，重复插入被约束挡住。
- **累加用 `UPDATE ... SET x = x + ?`**，并发下不丢计数；返回 0 行说明当天还没有这行。
- **金额 `decimal(12,6)`**：浮点累加会有漂移。
- **`currency` 落在行上**：换币种时历史行不受影响。

**为什么 `idx_cost_user_date_model` 不是 `(user_id, stat_date)`**：
查询是 `ORDER BY stat_date DESC, model ASC`，两个排序键都要在索引里才能免 filesort；只放 `stat_date` 会在有多个模型时退化成额外排序。

**间隙锁注意**：`UPDATE`（未命中）与 `INSERT` 必须在**不同事务**里。
`CostAccumulator.accumulate` 本身不加 `@Transactional`；`UPDATE` 走仓库方法自己的事务（提交即释放锁），没命中再调 `CostRowCreator.create`（`REQUIRES_NEW`）插入；撞唯一键则退回累加。详见 `usage/CostAccumulator.java`。

### 3.3 publish_record

| 索引 | 列 | 服务哪个查询 |
|---|---|---|
| `idx_status_scheduled_at` | `status, scheduled_at` | 扫到期：`WHERE status='SCHEDULED' AND scheduled_at <= now()` |
| `idx_status_claimed_at` | `status, claimed_at` | 扫卡死：`WHERE status='PUBLISHING' AND claimed_at < deadline` |
| `idx_publish_node` | `node_id` | 按节点查发布历史 |

要点：

- **两条索引对应两个定时任务**：到期扫描（每 5s）与卡死回收（每 30s）。它们扫的是**不同的列组合**，所以需要两条索引——只有 `(status, scheduled_at)` 的话，回收任务会退化成扫全部 `PUBLISHING`。
- **`claimed_at` 必须和 `status` 在同一条 UPDATE 里写**：否则"状态已改、时间没写"的记录会被回收任务误判成卡死。
- **状态推进一律条件更新**：`UPDATE ... WHERE id=? AND status=旧值`，影响行数 0 表示被别人抢先，不覆盖终态。

### 3.4 processed_task / failed_task

- `processed_task`：`task_id` 唯一，**去重靠约束不是靠"先查后插"**；插入冲突即说明重复投递，ack 跳过。
- `failed_task`：重试次数耗尽后落表（`attempts` 记录尝试次数），保留现场供人工补偿；`idx_failed_created` 支持按时间清理。

### 3.5 mq_outbox

- 业务先落 `PENDING`，投递器发送后由 confirm 改 `SENT`，消费回执改 `CONSUMED`。
- `uk_outbox_message (message_id)` 同时承担"业务幂等"：同一个 taskId 重复提交只留一行。
- `idx_outbox_status_retry (status, next_retry_at)` 服务扫描：`WHERE status='PENDING' AND next_retry_at <= now`。
- 对账按 `status='SENT' AND updated_at < 阈值` 找"投递了但没有消费回执"的记录重新投递。

### 3.6 api_key

- 只存**密文**与**脱敏串**，明文永不落库。
- `idx_apikey_owner (owner_id, id)` 服务"按归属人列表 + 按 id 倒序"。

### 3.7 cost_message_log

```sql
CREATE TABLE IF NOT EXISTS `cost_message_log` (
  `id`         bigint      NOT NULL AUTO_INCREMENT,
  `message_id` varchar(64) NOT NULL,
  `created_at` datetime(6) NOT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_cost_message` (`message_id`),
  KEY `idx_cost_message_created` (`created_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='成本消息去重';
```

- `message_id` = `user_query_log.request_id`，是成本消息的幂等键；
- 只服务"防重复"，不承担审计：保留 7 天，`CostReconcileJob.cleanupDedupeLog` 每天 03:00 清理；
- `idx_cost_message_created` 服务清理和"明细条数 vs 去重表"的按天对账。

## 4. 与 Hibernate 的约定

当前配置（`application.yml`）：

```yaml
spring:
  jpa:
    hibernate:
      ddl-auto: validate   # 结构由 docs/schema.sql 负责，应用只校验
```

改动表结构的流程：**先改 `docs/schema.sql` 与本文档 → 再手工执行 → 最后让应用启动校验通过**。应用本身不会自动改结构。

实体与 DDL 的类型映射：

| Java | DDL | 备注 |
|---|---|---|
| `Long` + `@Id` + `@GeneratedValue(IDENTITY)` | `bigint AUTO_INCREMENT` | 主键 |
| `String` + `@Column(length = n)` | `varchar(n)` | 长度必须一致 |
| `int` / `long` | `int` / `bigint` | — |
| `BigDecimal` + `precision = 12, scale = 6` | `decimal(12,6)` | 金额 |
| `Instant` | `datetime(6)` | 微秒精度 |
| `LocalDate` | `date` | 账期 |
| 枚举 + `@Enumerated(STRING)` + `@JdbcTypeCode(SqlTypes.VARCHAR)` | `varchar(16)` | 存名字，不存序号；不加 `@JdbcTypeCode` 时 Hibernate 6 会期望 MySQL 原生 `enum` |

> `validate` 只校验表与列是否存在、类型是否兼容，**不校验索引**。所以索引由 `schema.sql` 保证，本文档记录每条索引服务的查询。

## 5. 计费口径

| 项 | 规则 |
|---|---|
| token 估算 | 中文（CJK）1 字 ≈ 1 token，其余 4 字符 ≈ 1 token，向上取整，非空文本至少 1 |
| 单价 | `app.cost.pricing`，按 model 的冒号前缀取（`mock` / `openai`），取不到用 `default` |
| 金额 | `prompt_tokens × 输入单价/1000 + completion_tokens × 输出单价/1000`，`HALF_UP` 保留 6 位 |
| 失败调用 | 不计费（`cost_amount = 0`），不进聚合；明细仍落一行供排查 |

这套口径只保证**可解释、可复现**，与厂商真实账单无关。

## 6. 运维与演进

| 话题 | 现状 | 建议 |
|---|---|---|
| 明细增长 | 随对话线性增长 | 按 `created_at` 月分区，或定期归档到冷存储后删除 |
| 聚合表 | 一天一行，量很小 | 无需归档；可按季度汇总到年度表 |
| 失败任务 | `failed_task` 只增不减 | 按 `created_at` 清理 N 天前记录 |
| 时区 | 连接串 `serverTimezone=Asia/Shanghai` | 应用侧也固定 `-Duser.timezone=Asia/Shanghai`，避免 `LocalDate.now()` 与 DB 不一致 |
| 慢查询 | 明细按用户翻页 | 已由 `(user_id, id)` 覆盖；深分页改用"上一页最后 id"游标 |
