# 时序图：发布链路与 MQ 链路

> 两份图都对应实际代码路径，括号里是运行时线程名（可在 `logs/app.log` 里对照）。

---

## 1. 发布链路：抢占 → 执行 → 收尾 / 回收

涉及线程：`http-nio-*`（请求）、`scheduling-1`（调度）、`publish-exec-N`（执行池）。

```mermaid
sequenceDiagram
    autonumber
    participant C as 客户端
    participant CT as PublishController
    participant S as PublishService
    participant DB as PublishRepository (H2)
    participant SCH as PublishScheduler<br/>(scheduling-1)
    participant EX as PublishExecutor<br/>(publish-exec-N)
    participant H as PublishHandler

    rect rgb(238, 242, 255)
    Note over C,DB: ① 建单
    C->>CT: POST /api/publish?nodeId&delaySeconds
    CT->>S: create(nodeId, scheduledAt)
    S->>DB: INSERT status=SCHEDULED
    DB-->>S: id
    S-->>CT: record
    CT-->>C: {id, status=SCHEDULED}
    end

    rect rgb(236, 253, 245)
    Note over SCH,EX: ② 扫描并抢占（每 5s）
    SCH->>S: scanAndClaimDue()
    S->>DB: SELECT ... WHERE status=SCHEDULED AND scheduled_at<=now
    DB-->>S: [到期记录]
    loop 每条到期记录
        S->>DB: UPDATE SET status=PUBLISHING, claimed_at=now<br/>WHERE id=? AND status=SCHEDULED
        DB-->>S: 影响行数
        alt 影响行数 = 1（抢到）
            S->>EX: submit(execute(id))
        else 影响行数 = 0（被别人抢先）
            Note over S: 直接跳过，不重试
        end
    end
    end

    rect rgb(254, 249, 195)
    Note over EX,H: ③ 执行与收尾（publish-exec-N）
    EX->>S: execute(id)
    S->>DB: SELECT id=? 
    DB-->>S: record
    S->>H: publish(record)
    H-->>S: 正常返回 / 抛异常
    alt 成功
        S->>DB: UPDATE SET status=SUCCESS<br/>WHERE id=? AND status=PUBLISHING
        DB-->>S: 1
        Note over S: 日志 state advanced: true
    else 抛异常
        S->>DB: UPDATE SET status=FAILED, fail_reason=?<br/>WHERE id=? AND status=PUBLISHING
        DB-->>S: 1
    end
    end

    rect rgb(254, 226, 226)
    Note over SCH,DB: ④ 卡死回收（每 30s）
    SCH->>S: recoverStuck()
    S->>DB: SELECT ... WHERE status=PUBLISHING<br/>AND (claimed_at IS NULL OR claimed_at < now-timeout)
    DB-->>S: [卡死记录]
    loop 每条卡死记录
        S->>DB: UPDATE SET status=FAILED, fail_reason='stuck ...'<br/>WHERE id=? AND status=PUBLISHING
        DB-->>S: 影响行数
    end
    Note over S: 若执行线程这时才收尾，UPDATE 影响 0 行<br/>→ 日志 state advanced: false（不覆盖 FAILED）
    end
```

### 为什么这么设计

| 决策 | 原因 |
|---|---|
| `claimed_at` 与状态写在同一条 UPDATE | 分两条写会出现「状态已变、时间没写」，回收任务会把正在执行的记录误判成卡死 |
| 执行与回收都用条件更新 | 两个线程可能同时收尾；只有影响行数为 1 的那个算数，另一个自然落空 |
| 执行池用 `CallerRunsPolicy` | 队列满时回退到调度线程执行，形成背压；丢任务会留下永远停在 `PUBLISHING` 的记录 |
| 回收阈值独立于执行超时 | 执行耗时是业务属性，卡死阈值是运维属性，两者不该耦合 |

### 竞态时间线（实测）

```
t=0.0s   claimed（scheduling-1）
t=0.0s   publish 开始（publish-exec-1，耗时 5s）
t=5.0s   recoverStuck → FAILED（scheduling-1）
t=5.01s  execute 收尾 → UPDATE 影响 0 行 → state advanced: false
```

## 2. MQ 链路：投递 → 确认 → 消费 → 重试 / 落表

涉及组件：`RabbitTemplate`（生产）、`TaskConsumer`（消费）、`TaskProcessor`（事务内幂等 + 业务）、`failed_task`（兜底）。

```mermaid
sequenceDiagram
    autonumber
    participant C as 客户端
    participant TC as TaskController
    participant D as TaskDispatcher
    participant RT as RabbitTemplate
    participant MQ as RabbitMQ<br/>exchange / queue
    participant CS as TaskConsumer
    participant TP as TaskProcessor
    participant DB as H2<br/>processed_task / failed_task
    participant M as MeterRegistry

    C->>TC: POST /api/task/submit?payload&taskId
    TC->>D: dispatch(TaskMessage)

    alt app.mq.enabled = true（异步）
        D->>RT: convertAndSend(persistent, mandatory)
        RT->>MQ: publish
        MQ-->>RT: confirm(ack / nack)
        RT->>M: mq.publish.confirm{result}
        Note over RT: nack 或消息不可路由时记 error
        TC-->>C: "taskId (async via mq)"

        MQ->>CS: deliver（手动 ack）
        CS->>CS: attempt = header[x-retry-count] 或 0
        CS->>TP: process(message)  @Transactional
        TP->>DB: INSERT processed_task(task_id)  ← 唯一约束
        alt 处理成功
            TP-->>CS: 提交事务
            CS->>MQ: basicAck
            CS->>M: mq.consume.success
        else 唯一约束冲突（重复投递）
            DB-->>TP: DataIntegrityViolationException
            TP-->>CS: 抛出
            CS->>MQ: basicAck（跳过）
            CS->>M: mq.consume.duplicate
        else 业务抛异常
            TP-->>CS: 回滚（去重记录一并撤销）
            alt attempt < max-retries
                CS->>RT: republish(header x-retry-count = attempt+1)
                RT->>MQ: publish
                CS->>MQ: basicAck（原消息）
                CS->>M: mq.consume.retry
            else attempt >= max-retries
                CS->>DB: INSERT failed_task(reason, attempts)
                CS->>MQ: basicNack(requeue=false)
                CS->>M: mq.consume.failed
            end
        end
    else app.mq.enabled = false（同步降级）
        D->>TP: process(message)  @Transactional
        TP->>DB: INSERT processed_task + 业务
        TC-->>C: "taskId (inline, mq disabled)"
    end
```

### 为什么这么设计

| 决策 | 原因 |
|---|---|
| 去重记录与业务动作同一事务 | 若先提交去重再干活，业务失败后重试会被判成「重复消息」直接跳过，任务就悄悄丢了 |
| 失败用「重新投递 + 计数头」而不是 `nack(requeue=true)` | 立即重回队列会原地打转，把消费者钉死；带计数重投能限制次数，也能被别的实例接手 |
| 重试耗尽写 `failed_task` 再 nack | 毒消息留在队列里会反复投递；落表后既保留了现场，又释放了队列 |
| 生产端开 confirm + returns | confirm 回答「broker 收下没有」，returns 回答「收下但没有队列接收」，两者都缺就完全不知道投递结果 |
| inline 与异步共用 `TaskProcessor` | 幂等语义只有一处实现，降级时行为不会漂移 |

### 关键指标

| 指标 | 含义 |
|---|---|
| `mq.publish.confirm{result=ack\|nack}` | 生产端确认结果 |
| `mq.publish.returned` | 消息未路由到任何队列 |
| `mq.consume.success` | 正常消费 |
| `mq.consume.duplicate` | 唯一约束拦下的重复投递 |
| `mq.consume.retry` | 失败后重新投递 |
| `mq.consume.failed` | 重试耗尽，已写 `failed_task` |

查看方式：`GET /actuator/metrics/mq.consume.success`

## 3. 两张图的关系

发布链路和 MQ 链路是两条独立的路：发布走「状态机 + 线程池」，任务走「消息队列 + 消费者」。

共同点只有两条，也是这个项目想说明的重点：

1. **中间状态必须可恢复**：发布卡在 `PUBLISHING` 有回收任务，消息消费失败有重试与失败表。
2. **并发正确性靠数据库条件更新与唯一约束**，而不是靠加锁或「先查后写」。
